## Table and verify (de90b5e)

- `python tools/x3_counter.py table --runs ctr2-v92-k{K} --vars 1-29`: base (k0) 82 / 172, 89 counter rows, expected 171.
- **Bug found and fixed in the table writer:** its map key (width, height, groups, gems) came from tools/mapgen
  (mapio), which reads the map file's authored half, while the bot keys on the runtime `w.groups` (whole map). First
  verify: 83 / 172 (171 games identical to k0: no row fired); `--swap 1`: 81 (same). Mirroring the authored groups
  still left 34 maps wrong (137 / 172): some files list both halves' groups. Fix: a diagnostic build printed the bot's
  own fingerprint for every map and side (research/x3/counter_fp.json, 172 keys), and the writer now takes keys from
  that file (`--fp`). Patched tools/x3_counter.py on build/z-plan-5060.
- **Verify with exact keys (run ctr2-v92-table-fp, build 96612d0a188b, code section 892c71aae77b): 171 / 172 vs v92**,
  all 89 rows replay their variant's game exactly (0 mismatches). Fuel-outs 182 (k0 174), 0 faults.
- Files: results/J024-x1_counter.h (the table, generated with --fp), results/J024-counter_fp.json (the keys).

**Reading (facts):** the table is an exact counter to v92's deterministic play on these 86 maps: every covered loss
replays as a win. Against anyone else its choices are not counters (they beat v92's specific games), and it costs a
little: -4 vs v86h, -8 vs x1bru (neither past the noise floor, findings/0006), with x1bru fuel-outs up 166 -> 204.
On the real ladder the opponents are not v92, so this gain should not be expected there; it shows how much a
per-map, per-opponent table can win when the opponent's play is known exactly. Fuel: 182 vs v92 (k0 174).
